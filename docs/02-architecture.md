# 系统架构设计 v0.1

## 1. 架构与技术选择

采用模块化单体中心服务与独立浏览器执行器。单服务器用 Docker Compose 部署，默认使用嵌入中心服务的 SQLite，任务、数据和通知都以 SQLite 为持久化事实来源，不单独运行数据库容器。目标服务器 CPU 资源较低、内存充足，首版保持单中心进程、串行浏览器任务，不需要 Redis 或消息中间件。

| 单元 | 推荐方案 | 职责 |
|---|---|---|
| Web/PWA | Vue 3 + TypeScript + Vite + Vue Router + Naive UI（本轮推荐） | 管理、查询、安装与推送订阅；静态构建后由现有 NGINX 提供 |
| 中心服务 | Node.js + TypeScript + Fastify，独立 server 容器 | 用户认证、配置、调度、任务 API、入库、变化判断、通知 |
| 数据库 | SQLite（嵌入中心服务，WAL 模式） | 任务、租约、数据、事件、订阅、操作记录；数据库目录挂载本地持久化卷 |
| 浏览器执行器 | Node.js + CDP 客户端 + 有界面 Google Chrome | 插件运行、登录探测、结果暂存和上报；不引入 Playwright |
| 可视化环境 | Xvfb + 轻量窗口管理器 + VNC/noVNC | 用户进入同一服务器 Chrome 手动登录 |
| 入口 | 复用现有 NGINX、域名及 TLS | 静态前端、同源 API 代理及受控远程入口；项目不新建证书服务 |
| 推送 | 标准 Web Push + VAPID | 使用设备订阅端点发送；Apple 设备由其推送基础设施承载 |

版本在实施时锁定并实际验证。Chrome 由浏览器生命周期管理模块作为独立进程启动，使用专用持久化用户目录，人工桌面展示同一进程。执行器通过 WebSocket 直接发送 CDP 命令并订阅事件，可选择薄协议客户端（如 chrome-remote-interface），不引入 Playwright 或其他高层浏览器自动化框架。

针对现代 Chrome 的远程调试要求，使用明确的非默认用户目录；不尝试直接接管用户日常默认目录。CDP 端点限制在浏览器容器内部，通过进程管理发现地址，不经公网提供调试端口。连接断开不代表浏览器进程退出；重新连接时校验进程身份、档案锁和任务状态，不自动重放可能已发生的点击。

CDP 适配层负责 Target 页面会话管理、Page 导航、Runtime/DOM 数据提取、Input 点击输入、Network 事件与截图。需要自行实现条件等待、超时、iframe/新标签页处理、对象句柄释放、断连取消与诊断；协议记录须脱敏，并不是 Playwright trace。不得承诺直接 CDP 能避免站点检测或账号封禁；按站点规则控制频率，遇到验证或风险提示停止执行。

图见 [架构图](diagrams/system-architecture.drawio)。容量边界、前端候选对比、容器划分、现有 NGINX 路由和发布策略见 [技术选型与容量评估](05-technology-evaluation.md)。本轮前端推荐尚待用户最终选择；React 无业务实现需要迁移。

## 2. 中心服务模块

- 配置模块：插件注册信息、浏览器档案、任务参数、调度和通知规则。
- 调度模块：计算到期时间、补跑、创建持久化执行记录。
- 执行协调模块：领取、租约、心跳、阶段报告、取消、人工模式互斥。
- 数据模块：结构校验、业务去重、版本历史、完整性和变化事件。
- 通知模块：站内通知、事务 Outbox、设备投递、退避与失效端点清理。
- 管理模块：个人认证、审计、截图和 trace 访问、健康检查。

模块首版共用一个中心进程，后台循环异常不得静默终止；健康检查应暴露调度和通知循环最后工作时间。只有中心服务访问 SQLite，执行器和插件通过 API 读写业务状态，不挂载数据库目录。以后需要拆后台进程或部署多个中心实例时，先评估数据库并发与迁移方案。

### 2.1 SQLite 运行约束

- 数据库及其 `-wal`、`-shm` 文件所在目录整体通过 bind mount 挂载部署目录下的 `./data/database`，不放在容器可写层、Docker 默认命名卷或 NFS/SMB 等共享文件系统上。约定容器内目录为 `/data/database`，这是设计的虚拟路径，不是宿主机真实位置。
- 启用 `journal_mode=WAL`、`synchronous=FULL`，每个连接启用 `foreign_keys=ON`，建议 `busy_timeout=5000`。WAL 允许读写重叠，但同一时刻仍只有一个写事务。
- 数据访问层串行协调写入，事务尽量短；浏览器访问、推送发送、文件处理和大批量 hash 计算放在事务外。遇到 SQLITE_BUSY 使用有上限的退避，不让心跳被长事务阻塞。
- 中心服务选择受维护的 Node.js SQLite 驱动并锁定版本；同步驱动只执行短小有索引的查询，批量或耗时操作使用工作线程，避免阻塞事件循环。
- 建立任务到期时间、租约、业务键与 Outbox 到期时间等索引；分页查询有上限。监测 WAL 增长，空闲时执行适当 checkpoint，避免长读事务阻止回收，不在每次心跳强制 checkpoint。
- 调度器按下次到期时间休眠并设置低频兜底扫描，任务新增或修改时唤醒；空闲执行器采用长轮询或退避轮询。低 CPU 配置下避免高频空查询。

SQLite 减少独立服务和部署开销，但不会消除 Chrome 的页面渲染成本。默认单任务、及时关闭无用页面、仅失败保存 trace；Chrome 空闲时保留少量空白页面。若实测空闲开销仍高，可在无人操作且无任务时关闭 Chrome，下一次使用原用户目录启动并重新检查登录。

## 3. 执行器与浏览器生命周期

执行器定期领取任务，只允许一个活动执行。默认将部署目录 `./data/profiles`、`./data/spool`、`./data/artifacts` 分别绑定到容器 `/data/profiles`、`/data/spool`、`/data/artifacts`，Chrome 使用其中 `/data/profiles/main`。这些 `/data/...` 是容器内约定路径，不是宿主真实位置。容器重建保留部署目录数据，不再默认使用 Docker 命名卷；整体搬迁前正常停止服务并保留权限、符号链接，跨主机会话可能需要重登。

默认让 Chrome 保持运行以方便人工登录和保持会话；异常时由执行器管理重启。浏览器进程重启前必须确认旧进程已退出且用户目录锁已释放，禁止两份 Chrome 共用同一目录。任务结束关闭任务创建的页面，保留浏览器环境；定期回收内存需要避开人工操作和运行任务。

完整用户目录保存能力比仅导出 Cookie 更符合手动登录需求，但不能承诺网站无限期登录。网站可能基于有效期、IP、设备、二次验证等要求重新认证。

采用非 root 用户、可用的浏览器沙箱和资源限制；首个部署验证宿主机与沙箱兼容性，不把 `--no-sandbox` 当成默认生产配置。为 Chrome 配置合理共享内存；内存、CPU 的实际上限通过真实站点试跑测量。

## 4. 人工模式与互斥

浏览器档案模式为 `AUTO / MANUAL_REQUESTED / MANUAL / RECOVERING / PAUSED`。

1. 请求人工模式后停止新任务领取。
2. 当前任务自然结束，或明确取消并确认停止；中心不能只因租约到期就假设浏览器已释放。
3. 执行器确认无任务占用，进入 MANUAL，允许访问远程桌面。
4. 用户完成登录并结束人工模式，管理入口关闭，执行器做只读登录探测。
5. 探测成功转 AUTO，失败转 PAUSED 并给出处理原因。

状态转换与档案锁在数据库事务中维护；执行器还有本地互斥锁。断开 noVNC 不等于结束人工模式，以免用户误断线后任务突然接管。首版人工模式不自动超时恢复，而是提醒用户主动退出。

管理端账号认证与目标网站登录分别维护。远程桌面通过 VPN/SSH 隧道或经认证的短期会话访问；不公开暴露 VNC、CDP 或可绕过中心认证的 noVNC 服务。

## 5. 调度与任务恢复

### 5.1 每日调度

任务存储本地执行时间和 IANA 时区，计划时间转换为 UTC 存储。自动执行以 `(task_id, scheduled_for)` 唯一，调度器重启或重复扫描不产生重复记录。创建执行与推进下一次时间在同一事务内完成。

默认补最近 24 小时内的一次漏跑，更早计划记为跳过。人工处理恢复后复用同一计划记录；已有成功计划不再补跑。手动执行使用独立请求键，UI 防连点之外仍由服务端幂等。

如果后续配置夏令时地区：不存在的本地时间顺延至当天首个有效时刻，重复时刻只执行一次；需使用支持 IANA 时区的库并验证。任务禁用后不生成新计划，已有运行任务通过独立取消操作处理。

### 5.2 租约与崩溃

领取采用 SQLite `BEGIN IMMEDIATE` 短事务与带状态条件的更新，原子完成任务选择、档案互斥检查、租约和 token 更新；检查受影响行数，竞争失败则重新领取。SQLite 不使用行级锁或 `SELECT ... FOR UPDATE`。建议心跳 15 秒、租约 90 秒、只读任务默认最长 10 分钟，均可配置。每次领取产生递增 fencing token；所有执行写入携带执行器身份、attempt 和 token，拒绝旧持有者继续提交新的阶段结果。

执行器断联后必须在租约到期前主动停止页面操作；插件所有操作需受截止时间和取消信号约束。中心重新分配前先进入 RECOVERING：同一执行器确认旧任务停止，或由容器管理明确终止旧进程。不能确认时进入人工处理，不因 token 失效就认为外部点击已停止。

纯采集任务可重试；含签到任务先查操作日志并只读核验。fencing token 保护中心数据写入，不能撤销已经发往目标网站的点击。

## 6. 结果可靠上报

1. 插件产出数据和完整性标记，执行器以原子文件写入 spool，生成稳定 submission_id 与 payload_hash。
2. 调用入库接口；临时网络失败重传同一份结果，不重新访问网站或重做签到。
3. 中心在一次事务内完成提交去重、业务数据更新、版本/事件、站内通知和 Outbox。
4. 收到确认后删除暂存文件；重启时先恢复暂存提交。

超过租约的旧提交不能直接以旧 token 入库。恢复先核对旧执行已停止及当前持有者，再签发恢复 token；恢复 token 只恢复上报权限，不改变原采集顺序。是否允许更新数据，以已提交的采集顺序判断，与 task_run 是否 SUCCEEDED、PARTIAL 或尚未报告终态无关。已确认的 submission_id 重传在校验身份和 payload_hash 后返回原收据，不再次入库。

### 6.1 采集顺序与防覆盖规则（P1 修订）

首版采用**浏览器档案级提交水位**。档案内所有插件、任务和采集范围共用一个水位，即使业务范围不同也不能让较早采集在较新提交后入库。这是适合个人串行执行的保守选择：可能舍弃尚未入库的旧范围数据，但不会将其悄悄当成最新数据；原结果保留在过期归档，界面提示，并可安排一次新的只读采集。首版不自动合并旧批次中未冲突的实体。

1. 真正开始一次新的采集之前，中心在短事务中校验有效租约、档案独占权和旧执行已停止，为该次采集创建 `collection`，分配数据库全局单调递增 INTEGER `collection_seq`。它表达平台授权的串行采集顺序，不使用 worker 时间、scheduled_for、token 或任务终态排序。ID、序号、档案、执行及参数快照绑定后不可变。
2. 领取任务不自动产生新采集序号。仅恢复spool或已封存结果、重传、重新认证或更换租约时沿用原collection；禁止给旧结果换新序号。多步骤插件首次采集创建OPEN检查点，只有第6.3节规定的授权续采可以沿用原collection访问剩余队列。重新刷新列表、重做已完成步骤或已封存结果后重新抓取，均是真正新采集，必须登记新collection；旧结果保持原身份。新采集从重新导航/刷新并验证完成的页面读取，不能把旧spool或内存结果当成新观察。
3. 每个collection首版只允许一个封存后的不可变结果批次。OPEN阶段检查点可以原子推进，但不能作为最终submissions入库。中心确认封存时固定submission_id、业务载荷和hash，SEALED结果（包括partial）不再增补。签名/授权元数据（attempt、fencing token、恢复token）在业务hash外；业务hash覆盖collection_id、任务快照标识、scope_key、完整性、items和warnings。恢复上报时授权可更新，但业务内容和hash不变。
4. 入库使用 `BEGIN IMMEDIATE`，在**同一事务**内先查幂等收据，再校验当前提交权限、collection 绑定和档案水位。设 `incoming_seq` 为中心记录的序号，`committed_seq` 为档案最后接受序号：仅 `incoming_seq > committed_seq` 可应用新提交。等于水位但没有原收据是协议冲突，返回 409 并调查，不重新应用。
5. 接受提交时，实体更新、版本、变化事件、基线、通知/Outbox、submission 收据，以及档案 `committed_seq` 更新必须一起提交。即使内容指纹相同、结果是 PARTIAL 或有效空结果，也推进水位；不能依赖“新增版本”才推进。事务失败全部回滚。执行终态可稍后报告，不参与防覆盖判断。
6. `incoming_seq < committed_seq` 时整批判为 STALE：只保存不可变的过期收据与归档引用，不修改实体、last_seen、版本、基线或业务通知/Outbox，也不倒退水位。允许对过期结果另行产生一次去重的运维提示。返回 200 与 `disposition=stale`、归档确认后，worker 才可清理本地 spool；归档失败或没有中心确认时继续保留文件。
7. 原 submission 的收据查询优先于当前水位：已经 APPLIED 的提交即使后来水位更高、响应曾丢失，仍返回最初 APPLIED 收据；不能将它改判 STALE。同 ID 不同 hash、同 collection 不同 submission 均为 409，不创建新版本。

此规则同时覆盖跨任务、跨插件、同一执行的多个 attempt，以及新提交已入库但仍 RUNNING/PARTIAL 的情况。档案水位只能由入库事务推进，取消任务、失败上报、恢复租约和清理日志均不能重置。数据库序号分配器及水位一起备份恢复；数据与序号必须来自同一份一致性备份。

### 6.2 过期结果归档与恢复响应

过期归档是 P1 协议中的业务结果归档，不依赖暂缓的截图附件上传协议。首版采集批次有大小上限，中心将 STALE 业务载荷保存为 `run_submission.archived_payload`（JSON TEXT），和过期收据在同一事务提交；不发送大文件附件。不自动删除未确认归档，首版保留至用户明确清理；界面可在执行详情查看过期原因和归档摘要。

恢复接口返回 `replay_receipt`（已存在收据）、`authorize_upload`（已封存结果、旧执行已停止且无持有者冲突，可使用原collection上报）、`authorize_continue`（OPEN检查点满足第6.3节全部条件，可续采剩余队列）、`blocked`（仍占用/无法确认停止）或 `stale`（原采集低于水位，授权仅归档）。恢复检查只是预检，正式submissions及检查点续采接口必须在事务内再次检查条件；租约无效的worker不能利用stale分支绕过身份与归档授权。

如两个提交发生竞争，事务串行化决定可接受顺序：较早先入库可被后续较新采集更新；较新先入库则拒绝较早采集应用。真实采集内容由 A→B→A 时，只要是新的 collection 观察到 A，仍正常产生回退版本；旧 spool 的 A 不产生回退版本。

### 6.3 多步骤插件：OPEN续采与SEALED重传

collection执行生命周期区分OPEN（可变的本地工作检查点）、SEALED（一个固定submission_id/hash的提交载荷）与已应用/归档的终态。检查点不等于已封存结果，也不拥有中心提交权限。

OPEN中断后若要访问剩余队列，平台必须先确认旧持有者停止并重新取得有效租约与档案独占，事务校验：插件/参数/任务快照/原collection匹配；未封存、无原收据；未跨插件观察日期或原deadline；该档案无更晚登记的collection，且档案已提交水位未达到或超过原seq。通过后签发authorize_continue，保持原seq，只允许从原冻结队列恢复，禁止重读列表或改写已完成项。每次后续页面步骤前检查租约、取消与期限；不满足时停止页面访问。

只要新collection已经登记，旧OPEN就不能继续访问页面，即使新任务尚未提交；旧工作结果保留，可封存为partial并按当前水位规则应用或归档，但不能贴新seq。该保守规则避免新旧观察顺序交错，不放宽档案级提交保护。

完成/选择结束partial时，平台以有界seal请求核验原collection与检查点hash，将其CAS封存为SEALED，固定submission身份和业务hash；重复seal同hash返回原封存，不同hash冲突。中心封存状态持久化、worker落盘SEALED后才提交数据；响应丢失查询原封存，不能继续采集。submissions只接受与已封存hash匹配的批次。即使SEALED为partial，也只能重传或归档；要再抓网页必须新collection。用户取消可保留OPEN但不自动恢复，必须显式授权，或选择封存现有partial。

本地SDK阶段可用调用方授权hook测试上述规则，但不能声称已实现中心事务或替代真实授权；完整接线属于P2余下工作。

取消执行只阻止后续操作，不能撤销已发生的签到或已经提交的数据。取消与提交竞争由数据库事务决定，执行详情应准确展示已提交部分。

## 7. 变化、基线与通知

业务键为 `(source, profile_id, entity_type, source_key)`，区分同一网站不同账号环境。插件挑选稳定业务字段构建规范化内容指纹；抓取时间、展示顺序等不参与。

首次成功采集建立基线，产生一条汇总通知。后续新增或关注字段变化产生事件；相同指纹不创建新版本。部分采集可入库有效记录，但执行标为 PARTIAL，不建立完整基线、不推断删除；首次部分采集的逐条通知延后到完整基线摘要处理。

完整基线按 `(task_id, scope_key)` 维护，只有通过第 6 节顺序校验且完整成功的采集提交才推进。不同任务共享业务实体时，以当前版本指纹比较去重，站内变化事件由版本唯一标识去重，避免重复提醒；STALE 提交不推进基线或实体时间。

通知规则匹配后，事务中创建站内通知和 Outbox。后台针对每台设备记录投递，短暂失败退避，404/410 删除订阅。推送结果区分“推送服务已接受／重试中／永久失败”，不声称手机已展示或用户已读。通知点击进入站内详情，已读由前端明确回传。

## 8. 安全、备份与运维

个人使用仍需要管理端认证。建议首版单管理员登录、HttpOnly/Secure/SameSite 会话 Cookie，写接口校验 Origin/CSRF；执行器使用独立机器凭据，仅访问执行相关 API。服务器端校验插件允许访问的站点，防止参数误指向内网服务；公网推送端点也需 HTTPS 与网络访问边界校验。

插件视为可信部署代码，普通 UI 不提供任意代码上传。Cookie/Token/页面敏感字段不进普通日志，截图和 trace 按敏感文件管理。Chrome 数据卷、数据库备份和 VAPID 私钥仅管理员可读，凭据不入 Git。

每天使用 SQLite Online Backup API 或受支持的 `VACUUM INTO` 生成一致性数据库备份，并备份配置。不能在运行中只复制主 `.db` 文件而忽略 WAL；只有所有连接关闭后才能按离线方案复制。备份写入独立目标，按保留策略轮换，并定期恢复到临时目录执行 `integrity_check` 与 `foreign_key_check`。避免在执行窗口进行耗时备份。Chrome 用户目录采用停浏览器后的一致性备份；恢复到其他主机可能受平台密钥和网站风控影响，允许重新手动登录。VAPID 密钥需备份，丢失或更换可能需要设备重新订阅。诊断文件按保留期清理，未确认 spool 不自动清理；磁盘不足时停止领取并告警，不能静默丢结果。

最少观测项：服务/执行器心跳、调度延迟、最后成功采集、登录状态、连续失败次数、spool 大小、通知积压与磁盘容量。

## 9. 关键决策与后续边界

| 决策 | 原因 | 扩展触发条件 |
|---|---|---|
| 有界面 Chrome + 持久化档案 | 支持用户预先登录并复用同一环境 | 站点隔离需要更多档案 |
| 直接 CDP，禁用 Playwright | 遵循用户技术约束，显式控制真实 Chrome 与协议操作 | 特殊交互在 CDP 适配层补充；不自动更换框架 |
| 中心模块化单体 | 每日个人任务规模低、便于维护 | 后台负载明显增长再拆分 |
| 单执行器串行 | 减少账号竞争与人工接管复杂度 | 多站点执行时间不可接受时扩大并发 |
| SQLite 队列 + Outbox | 嵌入中心进程、短事务一致性、适合个人每日低写入量 | 多中心实例、持续写锁竞争或复杂查询成为瓶颈时，评估迁移 PostgreSQL |
| 代码插件、部署时安装 | 适合复杂站点且边界清晰 | 公共插件需另做隔离和供应链审查 |
